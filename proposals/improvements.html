2 · The main problem

How a result gets faked today

The server never runs the fight itself. Both phones run the same engine on the same inputs (this is called lockstep), so they see the same fight. The server only passes inputs between them and counts a round once both phones report the same score.

That works while both phones are honest. The trouble is that three kinds of message change the outcome, they all come straight from the phones, and one of them isn't checked at all.

Why snapshots exist. When a phone reconnects mid-fight, it has missed inputs. Both phones then restart the bout from one shared state: the round score, both fighters' health and the clock. The server sends restart_request to the phone that kept the fight going, and that phone answers with state_snapshot. Each restart gets a higher segment number.

The hole. The handler (server/multiplayer.py:1079–1093) accepts a snapshot from either player at any time, as long as its segment number is higher. clean_resume only clamps the values to their ranges: rounds 0–3, health 1–100. The opponent's phone loads it (game_pure.js:1890), and the engine writes the round score and health straight into the fight (umk3.js:16350–16365).

A second, smaller hole. settle_rounds (multiplayer.py:501) waits until both phones report the same score, with no time limit. A losing player whose phone never sends its final score keeps the match open. When the winner gives up and closes the app, the normal forfeit rule kicks in against the winner.

The rule behind both: never trust the client. Anything a phone sends can also be typed by hand. Telegram's signed login (initData) proves who sent a message, not that its content is true.

3 · Fixes

Fair results

F1, F5 and F6 are independent and small, and together they block both sequences above. F2 to F4 close the health part, which needs one decision from you.

F1 · Pin a snapshot's round score to the confirmed score

Do first
server/multiplayer.py · S · Needs nothing
Why
A snapshot can set any round score from 0 to 3, which ends the match on the spot.
Change
In the state_snapshot handler, accept resume.rounds only if it equals the confirmed score (room.p1_rounds, room.p2_rounds) or the score the other phone last reported in room.score_reports. Otherwise drop the snapshot. The second case covers an honest reconnect right after a knockout, before both reports have arrived.
Check
A test in TestHeroSelectAndRounds: a player sends a snapshot with rounds [0,2]; the opponent receives nothing and the match stays ACTIVE.

F2 · Route desync restarts through the server

game_pure.js, network_pure.js, multiplayer.py · M · Needs nothing
Why
Once a second, both phones compare a fingerprint of their fight (game_pure.js:1121). If they differ, P1's phone restarts both phones by sending a snapshot nobody asked for (line 1137). F3 can't allow only requested snapshots while this path exists.
Change
Both phones send a new {"type": "desync", "segment", "tick"} message instead. The server answers with restart_request to P1, the same message a reconnect uses. Allow one restart per 3 seconds per match, like the client's own guard today.
Check
A test: two desync messages for the same tick produce exactly one restart_request, sent to P1.

F3 · Accept only the snapshot the server asked for

server/multiplayer.py · S · Needs F2
Why
Even with the score pinned (F1), a forged snapshot can still set health and the clock whenever the cheater likes.
Change
When restart_bout sends restart_request (line 493), store room.pending_restart = (player_id, segment). The handler accepts a snapshot only from that player with that segment, then clears it.
Check
A test: an unrequested snapshot is dropped; the requested one is forwarded.

F4 · Restarted rounds start at full health

Decided: B
multiplayer.py, game_pure.js · S once decided · Needs F3
Why
After F3, the phone the server asks still reports the health, and the server can't check it. A cheater can get asked on purpose: if they send a wrong fingerprint, the opponent's phone reports a desync, and the server asks P1. P1 is whoever locks a hero first.
Option A
Keep trusting the phone. Smooth for honest players, since a reconnect continues the round where it was. But a cheater playing as P1 can still set health.
Option B
The server builds every restart: confirmed rounds, full health, fresh clock. The server already does this when neither phone kept the fight (line 495). It can't be faked, and every replay segment then starts from a state the server made, so N2 can re-check whole matches. The cost: a reconnect or desync replays the current round from full health.
Decided
B, on 2026-11-03, because the leaderboard ranks people. Also cap desync restarts at two per match and then end it as a no-contest (F6), so a losing player can't keep resetting rounds.

F5 · Settle on one report when the other phone stays silent

Do first
server/multiplayer.py · S · Needs nothing
Why
The second sequence above: silence keeps the match open until the winner leaves.
Change
When one phone reports a match-ending score and the other phone sends no score of its own for 15 seconds, or disconnects, finish with the one report. Use a task like the forfeit timer. Honest phones report within milliseconds, so only a modified or crashed phone is ever silent this long.
Check
A test: P1 reports 2–0, P2 reports nothing; after the timeout, match_ended names P1.

F6 · No-contest when the two reports disagree

Do first
multiplayer.py, db.py, bot.py · S · Needs nothing
Why
With F5 in place, a cheater who reports a fake win instead of staying silent gets two conflicting reports. Today that also hangs forever.
Change
If the two phones keep reporting different match-ending scores for 15 seconds, finish with reason DISPUTED and no winner. db.finish_match(..., record_stats=False) already exists for closing a match without touching the leaderboard (db.py:209). Keep the replay so N2 can settle it later. Add a DISPUTED line to result_line in the bot.
Check
A test: reports 2–0 and 0–2 lead to match_ended with reason DISPUTED, and no leaderboard row changes.

5 · Fixes

Server and bot

F13 · Stop creating a match on every inline query

Done, not committed
bot.py:364 · S · Needs nothing
Why
Telegram sends an inline query while the user types after @botname, and again each time they reopen it. Each one creates a WAITING row, even when nothing gets sent. The sweeper marks them CANCELLED later, and they stay in the table forever.
Change
Option (a): create the row in chosen_inline_result. That needs inline feedback turned on in @BotFather (/setinlinefeedback), and the handler already exists. Option (b): reuse the user's newest unsent inline challenge if it's under a few minutes old. (a) is cleaner. Its gotcha: a very fast tap on Play could arrive before the choice does, so the game should retry a NOT_FOUND once.
Done
Option (a). Inline feedback is on. The bot creates the match in handle_chosen_inline_result. For the fast tap, the server waits up to NEW_CHALLENGE_WAIT_SECONDS (3 s) for the match to appear instead of the game retrying. Four new tests cover it.
Check
Open inline mode five times and send nothing: no new rows.

F14 · Cap WebSocket message size

multiplayer.py:929 · S · Needs nothing
Why
aiohttp accepts messages up to 4 MB by default. rtc_signal (line 1071) forwards whatever it gets to the opponent, so one player can push megabytes onto the other's phone.
Change
web.WebSocketResponse(heartbeat=15.0, max_msg_size=64 * 1024). Real messages are far smaller; the largest is a WebRTC offer of a few KB. aiohttp closes a socket that sends more, with code 1009.
Check
A test: a 100 KB message closes the socket.

F15 · Relay only known binary packets

multiplayer.py:770 · S · Needs nothing
Why
relay_input forwards any binary frame to the opponent. The client only ever sends four kinds: 0x04 input (20 bytes), 0x05 and 0x06 ping and pong (4 bytes), and 0x07 fight fingerprint (12 bytes).
Change
Drop a frame whose first byte isn't 4 to 7, or that is longer than 20 bytes.
Check
A test: a 0x09 frame and a 500-byte frame don't reach the opponent.

F16 · Rate-limit text messages per connection

multiplayer.py:955 · S · Needs nothing
Why
Every net_stats message is logged at INFO (line 743), and every rtc_signal is forwarded. A loop sending them floods the log and the opponent.
Change
A token bucket per connection: a counter that refills at a steady rate, where each message spends one token and an empty bucket means "too fast". For example, 20 per second with bursts up to 60, which leaves room for the burst of connection candidates WebRTC sends. Ignore messages over the limit and close sockets far over it. Separately, accept net_stats at most once per 5 seconds (phones send every 10).
Check
A test: 500 net_stats in a row produce only a few log lines.

F17 · Save replays off the event loop

multiplayer.py:551–557 · S · Needs nothing
Why
The whole server is one asyncio event loop, and every match's inputs are relayed on it. finish() compresses the replay and writes it to SQLite right inside that loop. zlib and sqlite3 are blocking calls, so while they run, every other match's inputs wait.
Change
Run the compress-and-save in a worker thread: await asyncio.to_thread(...). Keep the order: write first, then broadcast match_ended.
Concept
async only lets other work run at an await. A blocking call inside async code stops everything until it returns.

F18 · Put /api/netstats behind a key

multiplayer.py:1136 · S · Needs nothing
Why
Anyone can read the latest 500 entries: match ids and each phone's user agent (line 741). That's diagnostics for you, not the public, and nginx proxies all of /api/.
Change
Require a key that matches NETSTATS_KEY from .env, and answer 404 otherwise.

F19 · Bot texts read the grace period from the server

bot.py · S · Needs nothing
Why
The grace period is RECONNECT_GRACE_SECONDS (multiplayer.py:32), but the bot hardcodes "60s" or "1 minute" in six places (bot.py lines 154, 234, 244, 287, 375, 383). If the constant changes, the bot's messages become wrong.
Change
Format the text from the constant, the way CHALLENGE_WINDOW_TEXT already does for the challenge window.

7 · New features

What to build next

These ideas build on parts that already exist: recorded inputs, match events sent to the bot, the matches table, and the rematch path that creates a match for a known pair of players.

N1 · Replay a match headless in Node

new tools/referee/ · L · Needs nothing
What
A command-line program that loads umk3.js in Node, plays a replay from /api/replay/<id>, and prints the final round score.
Why it can work
Lockstep already means the same inputs give the same fight on every device, which is how spectating and replays work today. The engine file has one direct browser reference. graphics.js and audio.js have seven each, and a headless run stubs those out: no drawing, no sound.
Unknown
How much of the replay driver in game_pure.js can run outside the browser.
Parked
This is a referee, not a way to watch. Once F1 to F6 are in, a cheater can at most turn a match into a no-contest. Build N1 and N2 only if the count of DISPUTED matches shows that really happens.
Check
For 20 stored replays, the program's score matches the recorded result.

N2 · Settle disputed matches from the replay

server · M · Needs N1, F6; best with F4 option B
What
When F6 ends a match as DISPUTED, the server runs N1 on its replay in a separate process, records the real winner, and has the bot edit the result message.
Limit
A replay segment that starts from a phone-supplied snapshot can't be checked. F4 option B removes those.

N3 · Player rating (Elo)

server/db.py, bot.py · M · Needs F1, F5, F6
Why
The leaderboard sorts by wins first (db.py, get_local_leaderboard). Whoever plays most ranks highest, and beating a strong player counts the same as beating a beginner.
How
Everyone starts at 1000 points. After a match, the winner takes points from the loser: more for an upset, fewer for an expected win (K = 32). Store them in a new ratings table, and update it inside the same transaction as finish_match, so a crash can't record half a result. Results have to be fair first, hence the dependency on F1, F5 and F6.
Decided
One rating per group, like the leaderboard.
Check
Unit tests for the math: two equal ratings move by exactly 16 each.

N4 · /history command

bot.py, db.py · S · Needs nothing
What
Your last 10 matches: opponent, both heroes, score, date, and a replay button.
How
Query matches by creator_id or opponent_id. The heroes and score are already stored in the room_state JSON column. Add indexes on those two id columns; today only chat_id and status are indexed.

N5 · /h2h head-to-head command

bot.py, db.py · S · Needs nothing
What
Reply to someone's message with /h2h to see your wins and losses against each other.
Why a reply
The Bot API can't look up a user's id from an @username, but a reply carries the user.

N6 · Quick match queue

multiplayer.py, bot.py, client · L · Needs nothing
What
A "Find a fight" button. The server keeps a queue, pairs the first two players in it, and creates their match the way a rematch does, with both players already set (multiplayer.py:676).
Blocker
In production only the bot creates matches (create=not auth_required(), line 805). The queue needs its own path for verified players.
Unknown
How many people are online at once. An empty queue feels broken, so show a count, or offer the CPU (N7).

N7 · Fight the CPU while a challenge is open

game_pure.js · L · Needs nothing
What
A challenge stays open for 10 minutes (CHALLENGE_WINDOW_SECONDS). Let the creator play the single-player mode meanwhile, and switch them into hero select when match_start arrives.
Unknown
Whether the engine can leave a single-player fight cleanly mid-round. A good sign: the client already fully resets the engine before every online bout (resetEngineForBout).

N8 · Group tournaments

bot.py, db.py · L · Needs nothing
What
/tournament in a group: 4 or 8 players sign up with a button, the bot posts the bracket, and each pairing becomes a match with both players set. Winners advance when the bot receives match_ended, an event it already gets (on_match_event).
Decide
What happens when a player doesn't show up. The challenge window could double as a walkover deadline.

N9 · Bot in the user's language

bot.py · M · Needs nothing
What
All bot text is English. Telegram tells the bot each user's app language (from_user.language_code). Move the strings into one table per language. In groups, use the language of whoever triggered the message.
Note
The game ships its own text in English, German, Spanish, French and Italian (player/assets/t_*). Which languages to add to the bot depends on who plays. For example, Russian and Uzbek, if that's your audience.

N10 · Report browser errors to the server

play.html, multiplayer.py · S · Needs F16
What
Today a JavaScript error on a player's phone is invisible to you. Catch window.onerror and unhandledrejection, send the message, a short stack, the build and the match id to a new /api/client-error endpoint, and log them there.
Needs
F16-style limits on the endpoint, so it can't flood the log.

N11 · Decide on a TURN relay from real data

network_pure.js:448 · S to decide, M to set up · Needs nothing
Why
WebRTC uses only STUN servers today, which find a direct path but can't relay. When the direct path fails, which is common on mobile networks, inputs go through the WebSocket over TCP, where one lost packet delays every packet behind it. A TURN server (coturn on the VPS) relays over UDP instead.
How to decide
Don't guess. Phones already report p2p, ice_failures and max_stall_ms every 10 seconds (/api/netstats). If most matches run without P2P and show long stalls, set up coturn. Otherwise skip it.
